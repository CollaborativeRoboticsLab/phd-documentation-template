\begin{abstract}
Generative robot planning systems can produce plausible behaviour plans from natural-language tasks, but they still tend to treat plan candidates as equally executable until failure occurs at runtime. This is a weak point for deployed robots, because a plan may be semantically relevant while still being slow, fragile, poorly grounded in available capability evidence, or mismatched to the robot's current state. We introduce \textit{Experience}, a planning layer that sits between capability discovery and execution and performs pre-execution plan assessment for Fabric-style execution graphs. Experience combines a semantic graph for capability and task meaning with a statistical graph for empirical execution evidence, then ranks candidate plans with a Risk-Aware Plan Feasibility Score (RAPFS) that balances predicted success, time, energy, fault burden, resource considerations, and epistemic uncertainty. This paper initializes the manuscript around the contribution's canonical thesis chapter: it defines the representation, the data-ingestion and retrieval paths, and the score formulation that makes the ranking process auditable. The current draft also records the present experimental state honestly: the conceptual and methodological core is specified, while the evaluation evidence is still being consolidated into paper-ready form.
\end{abstract}

\begin{keywords}
robot planning, pre-execution verification, ROS2, risk-aware planning, knowledge graphs, uncertainty-aware ranking
\end{keywords}

\section{Introduction}

Experience is a behaviour-planning extension that sits between capability discovery and execution. It is intended to consume semantic skill descriptions from Capabilities2 \cite{pritchard_capabilities2_2025, woodall_ros_2014}, observe runtime evidence from the wider ROS 2 system, and improve plan selection before a candidate plan is dispatched to execution. The motivation is straightforward: current generative robotics pipelines can produce plans that read well in language, yet they often forward every available capability description or telemetry fragment into a prompt and defer most feasibility questions until execution time. That pattern is expensive, hard to audit, and unsafe when the robot is operating under resource constraints or partial knowledge.

Recent work has shown that large language models can support long-horizon planning by grounding task descriptions in robot capabilities or scene structure \cite{ahn_as_2022, rana_sayplan_2023}. Behaviour-tree-based systems have pushed this further by generating structured intermediate plans rather than free-form code \cite{izzo_btgenbot_2024, zhou_llm-bt_2024, ao_llm-as-bt-planner_2025}. However, these systems still leave an important gap: candidate plans are rarely ranked using accumulated evidence about how capabilities perform under comparable contexts before execution begins. As a result, the planner may prefer a semantically plausible plan even when the robot has strong prior evidence that the same capability chain is unreliable, too slow, or poorly observed.

Contribution 2 addresses that gap. Rather than replacing the execution layer, Experience augments it with an evidence-aware planning stage. The central claim is that pre-execution plan assessment should combine two distinct forms of knowledge: semantic structure, which explains why a capability is relevant to the task, and empirical evidence, which estimates how that capability has behaved in comparable contexts. Keeping those roles separate is important because semantic similarity is not equivalent to execution reliability.

This paper makes three contributions. First, it defines a dual knowledge representation consisting of linked semantic and statistical graphs for capability-centric robotic planning. Second, it formulates a Risk-Aware Plan Feasibility Score that ranks candidate Fabric graphs using predicted success, cost, fault burden, and uncertainty. Third, it outlines a paper-ready evaluation framing for comparing pre-execution plan assessment against planner outputs that rely primarily on semantic generation alone. The current manuscript is an initial LaTeX draft seeded directly from the canonical Contribution 2 markdown, so the methodological core is present while the final empirical section still requires synchronization.

\section{Related Work}

Generative robot planning has moved from direct code generation toward intermediate symbolic structures that can be checked or executed more reliably. SayCan and related systems demonstrated that language-model planning becomes more useful when high-level actions are grounded in embodied capabilities instead of being treated as pure text generation \cite{ahn_as_2022}. SayPlan extended this pattern with scene-graph-based retrieval and iterative refinement for long-horizon tasks \cite{rana_sayplan_2023}. These systems established the value of selective grounding, but they do not by themselves provide a general pre-execution score that compares multiple candidate execution graphs using accumulated runtime evidence.

Behaviour-tree generation systems make the intermediate representation more explicit. BTGenBot, LLM-BT, and LLM-as-BT-Planner show that structured behaviour plans can be generated, validated, and in some cases adapted during execution \cite{izzo_btgenbot_2024, zhou_llm-bt_2024, ao_llm-as-bt-planner_2025}. Their main strength is that the planner output is no longer opaque code. Their main limitation for the present problem is different: a valid plan syntax does not tell us whether the selected plan is the most reliable or feasible one for the current robot state, time budget, or evidence history.

At the capability layer, the original ROS capabilities work and its ROS 2 successor address a different but necessary problem: how robot skills are described, loaded, and composed in a standard way \cite{woodall_ros_2014, pritchard_capabilities2_2025}. Experience builds on that foundation. Capabilities2 provides a structured representation of available robot functionality, but it is not itself a plan-ranking framework. Experience uses those descriptions together with execution evidence to estimate whether a candidate plan is likely to succeed before it is run.

The resulting position of this work is therefore narrower and more specific than a full planner replacement. Experience is not another LLM interface and not another execution engine. It is an evidence-aware ranking layer placed between generation and execution. That placement is motivated by a simple observation from the broader fault-tolerance and verification literature: acceptable plans are not defined only by semantic correctness, but also by timing, energy, uncertainty, and the system's ability to justify the choice it made.

\section{Methodology}

\subsection{Problem Formulation}

Let the planner produce a finite candidate set of execution plans,

\begin{equation}
\mathcal{P}=\{G_{\pi_1}, G_{\pi_2}, \ldots, G_{\pi_m}\},
\end{equation}

where each candidate plan is a directed execution graph,

\begin{equation}
G_{\pi}=(V_{\pi}, E_{\pi}).
\end{equation}

Each node corresponds to a capability instance or system runner, and each edge represents an execution relationship or triggering condition inherited from the underlying Fabric plan semantics. The planning problem is not only to generate these graphs, but to rank them before execution using evidence that is conditioned on the task, context, and prior runtime history.

\subsection{Dual Knowledge Representation}

Experience uses two linked graphs as its knowledge store. The semantic graph captures meaning: capability descriptions, task entities, context entities, reusable plan patterns, and fault concepts. It supports retrieval questions such as which capabilities are relevant to the task, which dependencies frequently co-occur, and which recovery structures are semantically similar to the current problem. The statistical graph captures measurement: execution success and failure counts, duration, battery or energy usage, observed fault frequencies, and uncertainty-relevant metadata.

The graphs share stable capability and context identifiers but remain logically separate. This separation prevents a common modeling mistake in generative planning: treating semantic relevance as if it were probability of success. A capability can be a strong semantic match for the user's request and still be a poor operational choice because its empirical evidence is sparse or negative.

\subsection{From Evidence to Node Features}

For each capability instance $i$ in a candidate graph, Experience estimates a feature vector,

\begin{equation}
x_i = [p_i, t_i, e_i, f_i, \mathbf{r}_i, u_i],
\end{equation}

where $p_i$ is estimated success probability, $t_i$ is expected execution time, $e_i$ is expected energy cost, $f_i$ is expected fault burden, $\mathbf{r}_i$ is a resource-demand vector, and $u_i$ is epistemic uncertainty. The write path into this representation is driven by four input classes: runtime observations, capability metadata, prior plan history, and external task context. The read path resolves candidate plan nodes to stable IDs, retrieves semantic neighbors and statistical rows, selects the most specific reliable evidence available, and raises uncertainty when broader fallbacks or missing telemetry are required.

In the current formulation, quantitative resource telemetry is not yet fully available, so the resource vector remains a declared part of the model while its hard constraint can remain inactive during early evaluation. That omission does not invalidate the score design; it simply means missing resource evidence is carried explicitly through the uncertainty term instead of being replaced with fabricated measurements.

\subsection{Risk-Aware Plan Feasibility Score}

The Risk-Aware Plan Feasibility Score ranks candidate plans using

\begin{equation}
\operatorname{RAPFS}(G_{\pi}) =
 w_s S(G_{\pi})
 - w_t \hat{T}(G_{\pi})
 - w_e \hat{E}(G_{\pi})
 - w_f \hat{F}(G_{\pi})
 - w_r \hat{C}_r(G_{\pi})
 - w_u \hat{U}(G_{\pi}),
\end{equation}

where $S(G_{\pi})$ is terminal success probability, the hatted terms are normalized plan-level costs, and the nonnegative weights encode the deployment trade-off. The score is intentionally interpretable: each term corresponds to a distinct source of concern rather than collapsing everything into a single opaque reward.

The uncertainty term is especially important. Experience does not treat failure probability and uncertainty as the same quantity. Low success probability indicates that a plan is estimated to fail. High uncertainty indicates that the estimate itself is weak because of sparse evidence, ambiguous task grounding, unfamiliar context, or missing telemetry. Those cases should be handled differently by the planner.

\subsection{Feasibility Constraints and Feedback}

The ranking stage is paired with hard feasibility checks over time, energy, terminal success, and eventually peak concurrent resources. In practice, Experience is intended to reject plans that violate declared limits before execution, and to log the evidence and estimator versions that produced the decision. That logging matters because plan-quality feedback may later be used to improve component estimates and, on a slower timescale, adjust scoring weights in versioned evaluation epochs.

This design keeps the system auditable. New runtime evidence should primarily update the component estimates, not silently change the meaning of the score from one decision to the next. Weight adaptation is therefore treated as an explicit, slower process tied to logged plan outcomes rather than an uncontrolled online drift.

\section{Evaluation Framing and Current Status}

The evaluation goal for Experience is different from the earlier GPSFSM manuscript that previously occupied this file. The relevant question here is not whether a model can emit a valid execution graph from text alone, but whether pre-execution ranking improves the choice among candidate plans under uncertainty. The chapter material suggests three evaluation surfaces.

First, the score should be tested for ranking quality: whether plans with higher RAPFS are more likely to succeed than lower-ranked feasible alternatives under comparable requests. Second, its components should be checked for calibration, especially the terminal success estimate and the uncertainty signal. Third, the ablation boundary should be explicit: semantic retrieval alone, semantic plus empirical evidence, and fixed versus slowly adapted weights are distinct systems and should not be conflated.

At present, the contribution's canonical markdown contains the strongest material in the introduction, literature framing, and methodology subsections, while the standalone results section is still an assembly point rather than a consolidated empirical narrative. This LaTeX draft therefore keeps the paper honest: it defines the experiment logic and the claims that can be defended now, without copying unrelated GPSFSM results into an Experience manuscript. The next synchronization step should convert the thesis-side evaluation notes and any experiment repository evidence into paper-ready tables, baselines, and calibration plots.

\section{Conclusion}

Experience is intended to make generative robot planning more selective and more defensible before execution begins. Its core idea is simple: plan candidates should not be ranked only by how well they match the task in language, but also by how well prior evidence suggests they will execute under the current conditions. The dual-graph representation and RAPFS formulation provide that bridge between semantic relevance and empirical feasibility.

This initial paper draft captures the contribution's conceptual center from the canonical Contribution 2 markdown source. What remains unfinished is primarily empirical packaging, not the architectural argument. The next stage is to consolidate the evaluation evidence into a paper-specific results section that tests whether Experience improves plan ranking, calibration, and failure avoidance relative to generation-only baselines.
