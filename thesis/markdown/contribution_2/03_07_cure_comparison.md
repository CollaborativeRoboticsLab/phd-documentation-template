# CURE Comparison And Verification Status

This document tracks which verification issues have been addressed by the Risk-Aware Plan Feasibility Score (RAPFS) formulation and which still require implementation or empirical validation. **Resolved** means the mathematical specification now addresses the issue. It does not imply that the required estimator, calibration data, feedback loop, or deployment test has already been implemented. Where useful, this document distinguishes between specification-only resolution and partial implementation progress.

## Foundational Formulation Issues

| Issue | Status | RAPFS resolution | Remaining work |
|---|---|---|---|
| Plan representation | **Resolved** | Candidate plans are event-labeled directed execution graphs $G_\pi=(V_\pi,E_\pi)$ matching Fabric connections. A sequential plan is explicitly the chain-graph special case. | Implement conversion from each generated candidate into the scoring graph representation. |
| Aggregate functions | **Resolved** | Time is expected scheduled makespan; energy and faults are expectations over execution scenarios; parallel resource demand is computed from concurrently active nodes. | Choose or implement the scheduler and execution-scenario inference method. |
| Multidimensional resources | **Resolved in specification; telemetry missing** | Capability demand is $\mathbf{r}_i$ and feasibility uses a componentwise upper quantile of peak concurrent demand against $\mathbf{R}_{\max}$. Consumable resources use separate cumulative budgets. In the current instantiation, resource feasibility is inactive and $w_r=0$ until quantitative telemetry exists. | Define the measured resource dimensions and estimate their per-capability distributions. |
| Incommensurate uncertainty components | **Specified; calibration pending** | Statistical uncertainty, ambiguity, unfamiliarity, and missing evidence are separately normalized to $[0,1]$ before weighted combination. | Fit and validate the normalization and calibration mappings on held-out data. |
| Capability dependence | **Resolved in specification; partially implemented at capability level** | Plan success is terminal-event probability $S(G_\pi)$ under graph and context-conditioned node outcomes. The product $\prod_i p_i$ is restricted to an independent critical chain. The supervisor now publishes event-derived per-capability run evidence, so capability-level success rates can be estimated from `TRIGGERED`, `SUCCEEDED`, `FAILED`, and `TERMINATED` counters. External plan-success feedback can also update plan-level evidence for $S(G_\pi)$. | Implement exact graph inference or Monte Carlo simulation for plan-level success and learn the required conditional models. Validate that every triggered run emits one terminal outcome under deployment conditions. |
| Resource propagation | **Resolved for RAPFS** | Resource operating cost appears in RAPFS, while multidimensional peak demand appears in hard and soft feasibility formulations. | Propagate the same treatment into the Bayesian and MDP or POMDP formulations before comparing them. |
| Overloaded symbol $R$ | **Resolved for RAPFS** | $\mathbf{R}$ is reserved for resources and $Y(G_\pi)$ denotes random realized score in the variance extension. | Audit the Bayesian and Markov documents for the same convention. |
| Weight feedback | **Specified; empirical validation pending** | External plan-success feedback updates component estimates continuously and may update RAPFS weights only at evaluation epoch boundaries through versioned learning-to-rank or Bayesian posterior updates. | Collect pairwise or outcome-based feedback, control selection bias, and validate whether updated weights improve held-out ranking quality. |

## Status of Issues Identified From the CURE Paper

The uncertainty term should also be interpreted in light of Yin et al., [*Towards Reliable LLM-based Robot Planning via Combined Uncertainty Estimation*](https://arxiv.org/abs/2510.08044) (CURE, arXiv:2510.08044v1). CURE separates epistemic uncertainty into task ambiguity and task unfamiliarity, and models intrinsic uncertainty through expected execution success. This supports a richer decomposition than a single undifferentiated $u_i$, but it also exposes the following issues for this framing:

1. **Uncertainty source and failure probability are not interchangeable.** CURE uses predicted execution success in its uncertainty score, but an observed failure can result from planner error, capability failure, perception error, resource exhaustion, or environmental randomness. Defining intrinsic uncertainty as $1-p_i$ without a causal or conditional model risks mixing these sources and double-counting failure risk. **Status: Resolved in the RAPFS specification.** $S(G_\pi)$ carries predicted terminal success, $u_i$ carries epistemic uncertainty, and realized execution variability is isolated in the optional variance term.

2. **Uncertainty needs calibration, not only ranking quality.** CURE is evaluated mainly using Spearman correlation and a help-rate/success-rate AUC, and the authors explicitly state that its output is not calibrated to actual success rates. A score that ranks two plans correctly is not necessarily a probability and cannot safely be compared with a fixed execution threshold. **Status: Partially resolved.** RAPFS is explicitly a ranking score, while $S(G_\pi)$ is the separately calibrated probability. Capability-level success evidence is now published from terminal events, and external plan-success feedback can calibrate plan-level outcomes, but the calibration model and held-out evaluation for $S(G_\pi)$ still need to be implemented.

3. **The sign convention must be explicit.** The paper writes an objective that maximizes correlation between success and uncertainty even though larger uncertainty should normally correspond to lower success; its experiments often discuss confidence instead. **Status: Resolved in the RAPFS specification.** Every $u_i$ component is oriented so that a larger value means greater uncertainty, and RAPFS subtracts the resulting plan-level penalty.

4. **Component scales must be bounded before combination.** CURE combines ambiguity, predicted success, and raw Random Network Distillation (RND) error using tuned coefficients, including a large novelty coefficient. Raw RND distance is not inherently bounded, so the resulting quantity need not lie in $[0,1]$. **Status: Specified; calibration pending.** RAPFS requires every uncertainty component and hatted cost to be mapped into $[0,1]$ by a declared, fixed transform. Those transforms still need to be fitted and validated.

5. **Novelty is not the same as semantic distance or risk.** CURE calls its RND prediction error a similarity measure even though larger values indicate greater dissimilarity or unfamiliarity. **Status: Resolved in the RAPFS specification.** The term is named unfamiliarity, raw retrieval distance is passed through a bounded calibration map, and unfamiliarity is not treated as execution failure probability.

6. **Offline task-specific training limits transfer.** CURE requires pretrained task-specific data, performs poorly in unseen environments, and identifies lack of generalizability as a limitation. **Status: Partially resolved.** RAPFS requires distribution-shift detection, an increased unfamiliarity penalty, and a conservative fallback. The knowledge store can accumulate context-conditioned evidence over time, but validation across task, environment, and robot changes remains open implementation work.

7. **Planner independence is limited in practice.** Although CURE is described as plug-and-play, its fast estimator consumes hidden activations from a particular frozen LLM and needs supervised training. **Status: Resolved architecturally.** The RAPFS estimator interface is defined around planner-independent context, telemetry, graph, and retrieval outputs; hidden LLM activations are optional rather than required.

8. **Plan-level and capability-level uncertainty are different.** CURE estimates uncertainty after an LLM generates a whole high-level plan, whereas $u_i$ is attached to each capability instance. **Status: Resolved in the RAPFS specification.** RAPFS defines a scenario-weighted mean over executed graph nodes and a conservative maximum over all reachable nodes, covering parallel and recovery paths. The experiment must choose one aggregation rule before evaluation.

9. **The paper does not model the resource trade-offs in this objective.** CURE assesses whether to execute, halt, or request help, but it does not jointly optimize execution time, energy, faults, or multidimensional resources. **Status: Resolved for RAPFS specification.** RAPFS includes normalized time, energy, fault, resource-cost, and uncertainty terms, plus multidimensional hard or soft resource constraints. In the current implementation, the resource term is disabled until quantitative telemetry exists. CURE remains an input to uncertainty modeling rather than the complete plan-ranking objective.

10. **The evaluation assumptions are stronger than deployment conditions.** The paper's help-rate metric assumes requested human assistance guarantees success, and its experiments cover two constrained manipulation settings. **Status: Open empirical work.** RAPFS specifies reporting success calibration, constraint violations, resource peaks, individual score components, and external plan-success feedback, but cost-sensitive false-confidence tests, distribution-shift tests, long-horizon evaluation, selection-bias controls, and real resource-failure experiments still need to be designed and run.

RAPFS now treats uncertainty as a structured, context-conditioned object before reducing it to a scalar ranking penalty. It retains separate estimates for statistical uncertainty, task ambiguity, task unfamiliarity, and missing evidence, while environmental or execution variability remains separate in the optional risk-sensitive extension. On the implementation side, the supervisor
now publishes event-derived capability run evidence, so capability-level success and outcome-type counters are no longer purely hypothetical. External plan-success feedback is also specified as plan-level evidence for calibrating $S(G_\pi)$ and, at epoch boundaries only, for adapting RAPFS weights.

The main remaining work is implementation and validation: fit calibration maps, estimate graph-conditioned terminal success, simulate or infer execution scenarios, measure resource distributions, define the out-of-distribution fallback, validate event-outcome semantics, control selection bias in feedback, and evaluate RAPFS on held-out and shifted deployment conditions.
