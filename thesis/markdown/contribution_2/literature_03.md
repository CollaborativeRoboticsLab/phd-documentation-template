# Fault Tolerance at the Middle Level

Middle-level fault tolerance concerns the software and subsystem layer that connects hardware capabilities to task execution. In contemporary robotic systems, this level is heavily shaped by middleware, lifecycle management, subsystem isolation, and recovery orchestration. Within ROS 2, fault tolerance is no longer treated as an afterthought but is embedded into communication policies, managed node states, diagnostics aggregation, and the planning frameworks used by navigation and manipulation stacks. The goal at this layer is not merely to detect physical faults, but to contain failures in communication, timing, perception, planning, and software integration before they propagate across the system.

ROS 2 provides several native mechanisms that can be interpreted as safety contracts between publishers, subscribers, and supervisory components. Quality-of-service policies are central to this. Liveliness and lease durations act as distributed software watchdogs by requiring publishers to periodically assert that they are still active; if they do not, subscribers can infer a node crash, network partition, or hung driver without continuous polling. Deadline policies add timing guarantees by detecting whether messages arrive within the required interval, which is especially important for control loops that cannot safely operate on stale commands or sensor samples. Durability policies, particularly transient local durability, allow restarted nodes to recover the most recent important state such as maps or configuration data rather than rejoining the system blind. Together, these mechanisms give middleware-level meaning to failure and recovery.

Managed lifecycle nodes extend this idea by making node state explicit. Instead of treating components as simply running or stopped, ROS 2 lifecycle nodes move through states such as unconfigured, inactive, active, and finalised. This structure supports deterministic restart behaviour because a supervisor can command cleanup, reconfiguration, and reactivation in a controlled sequence. It also improves fault isolation: nodes can be fully initialised before they are allowed to publish or execute, reducing the risk that partially configured drivers contaminate the rest of the system with invalid outputs. The diagnostic stack provides a complementary observability layer by collecting hardware and software health reports and restructuring them into summaries that humans or higher-level monitors can consume more effectively than raw diagnostic traffic.

The navigation stack in ROS 2, particularly Nav2, demonstrates how these middleware capabilities become concrete recovery behaviour. Nav2 replaced the monolithic control logic of earlier navigation systems with behaviour-tree-based orchestration, which makes recovery modular and context aware. A recovery node can attempt a primary behaviour such as path following and, on failure, invoke a targeted corrective action such as spinning in place, backing up, or clearing a local costmap before retrying. This allows the system to escalate recovery gradually, trying cheaper or less disruptive options before abandoning the task. Just as importantly, Nav2 separates planning and control into distinct lifecycle-managed servers, so that failure in the global planner does not immediately eliminate the controller's ability to stop safely or perform local reactive behaviours.

Manipulation stacks face a different but equally demanding recovery problem because they operate in higher-dimensional state spaces and are tightly coupled to dynamic perception. MoveIt 2 addresses this through layered mechanisms rather than a single global recovery manager. Perception-induced planning failures, such as stale or phantom obstacles in an octomap, can be mitigated through map-clearing behaviours, but the success of those behaviours depends on the point-cloud and scene-update pipeline remaining healthy. Real-time servoing provides another recovery layer by allowing continuous velocity control outside the slower sense-plan-act loop, which is crucial near kinematic singularities or imminent collisions. By scaling commands near singular configurations and continuously checking collision proximity, MoveIt Servo acts as a software safety buffer beneath the higher-level planner.

The hybrid planning architecture in MoveIt 2 further illustrates the middle layer's role in fault tolerance. Rather than stopping the robot completely every time the environment changes, hybrid planning decouples slower global planning from faster local execution. When the local planner becomes stuck because of a dynamic obstacle or execution failure, it can report that event upward while the global planner computes an alternative route. This structure preserves continuity of operation and makes replanning a coordinated subsystem response rather than a full reset. MoveIt Task Constructor pushes the same principle into task composition by allowing alternative planners, fallback strategies, and parallel planning structures to coexist inside a single task representation. This enables graceful degradation from optimal strategies to merely feasible ones when constraints tighten or preferred methods fail.

Physical interaction failures occupy an important boundary between the middle and low levels. Slip detection, reflexive regrasping, and visual servo correction all depend on immediate sensing, but their orchestration often sits above pure feedback control. In practice, the manipulator may need to combine tactile or force cues, state estimation, and a behaviour-level recovery policy to decide whether to retry, regrasp, or abandon a step. This again favours modular execution frameworks, especially behaviour trees, because they let the system embed reflexive safeguards while preserving a readable task structure.

Log-based fault detection provides another major capability at the middle layer because many subsystem failures are semantic or infrastructural rather than purely dynamic. A planner crash, transform timeout, configuration mismatch, or degraded sensor driver can produce cascading errors across the stack even when the physical robot appears stationary. Template-based log parsing is often too brittle for this environment, which has driven interest in semantic analysis frameworks such as LogLLM. These systems use language models to interpret sequences of log messages, detect unusual causal patterns, and sometimes connect them with retrieved troubleshooting knowledge. Their value is not just anomaly detection but contextual diagnosis: instead of merely flagging that an error occurred, they help explain whether the likely root cause is a network issue, a synchronization failure, a device disconnect, or a configuration conflict. The literature therefore suggests that middle-level fault tolerance is fundamentally architectural. It depends on how subsystems are decomposed, how communication contracts are enforced, how recovery is escalated, and how semantic evidence from diagnostics and logs is integrated with behavioural control. The remaining gaps are also architectural. Navigation and manipulation stacks still implement recovery using different abstractions, and there is no universally adopted cross-stack notion of system health. As robots become more heterogeneous and more dependent on distributed software, a unified supervisory framework that coordinates lifecycle control, diagnostics, log semantics, navigation recovery, and manipulation replanning remains an open research need.
