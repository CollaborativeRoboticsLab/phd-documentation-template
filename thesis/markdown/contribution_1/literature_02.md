# Behaviour Trees and FSM for Behaviour Representation in Robotics

Behaviour Trees (BTs) and Finite State Machines (FSMs) remain two of the most common abstractions for representing robot behaviour, especially in manipulation and mobile manipulation tasks. A useful comparative framing is provided by [Comparison between Behavior Trees and Finite State Machines], where both approaches are evaluated using the same low-level robot skills and differ only in the high-level container, that is, a behaviour node in the BT case and a state in the FSM case.

In that comparison, BTs are described as directed trees evaluated in depth-first order, with control nodes such as Sequence, Fallback, and Parallel coordinating execution, and execution nodes such as Action and Condition returning Running, Success, or Failure [Comparison between Behavior Trees and Finite State Machines]. This uniform interface makes BTs modular by construction, since each subtree can be reused as an independent building block without changing the overall policy structure. The same structure also supports separate testing of individual subtrees. Reactivity is one of the strongest advantages of BTs, because the Running status allows the tree to be reevaluated at every tick and enables preemption when a higher-priority behaviour must take control [Comparison between Behavior Trees and Finite State Machines]. The paper also notes that BT design can be guided by criteria such as execution time, success probability, or action cost, and cites work where the robot selects the lowest-cost subtree at runtime [Comparison between Behavior Trees and Finite State Machines].

FSMs, by contrast, are rooted in state automata and represent behaviour as a set of states connected by transitions [Comparison between Behavior Trees and Finite State Machines]. Each state encodes a controller whose execution changes the environment, and those effects trigger events that move execution to the next state. This representation can be effective, but the same paper argues that strong reactivity often requires a large number of explicit transitions, which reduces modularity and scalability [Comparison between Behavior Trees and Finite State Machines]. Hierarchical FSMs can mitigate this to some extent through grouping, while parallel composition can improve modularity by allowing independent subtasks to be designed separately and later composed automatically [Comparison between Behavior Trees and Finite State Machines]. Even so, FSM edit operations remain comparatively costly because the switching logic is typically embedded inside the states rather than being explicitly represented in a reusable control structure [Comparison between Behavior Trees and Finite State Machines].

The discussion of reactivity in [Comparison between Behavior Trees and Finite State Machines] is especially relevant for robotics. A controller should react when part of a task has already been completed, or undone, by an external agent or disturbance, so that it can skip unnecessary steps or redo invalidated ones. It should also interrupt the currently executing action when a higher-priority requirement arises, such as recharging under low battery conditions [Comparison between Behavior Trees and Finite State Machines]. These requirements highlight why BTs are often preferred when runtime interruption, reevaluation, and explicit priority handling are central design concerns.

More recent work extends BT-based behaviour representation beyond handcrafted control design by integrating large language models. [Automatic Behavior Tree Expansion with LLMs for Robotic Manipulation] proposes using an LLM not only for interpreting goals, but also for resolving execution and planning errors that fall outside the capabilities of the planner. The key idea is to use the LLM output to automatically and permanently expand or update the BT policy, thereby improving success rate and robustness while preserving transparency and readability [Automatic Behavior Tree Expansion with LLMs for Robotic Manipulation].

This paper positions its method against earlier LLM-guided BT generation approaches. In the LLM-BT formulation, a parser is used to translate model responses into BT nodes, whereas LLM-OBTEA relies on stricter prompting to obtain goal conditions with minimal parsing and adds a reflective feedback stage that repeatedly sends syntax errors back to the model until a valid structure is produced [Automatic Behavior Tree Expansion with LLMs for Robotic Manipulation]. The authors argue that improved prompting and a stronger LLM eliminate the need for reflective feedback, reducing the number of LLM calls while still producing better results [Automatic Behavior Tree Expansion with LLMs for Robotic Manipulation]. Conceptually, this contributes to two important themes for behaviour representation: sequential program generation and failure resolution through policy expansion rather than full redesign.

Taken together, these two papers suggest a useful trajectory for the literature. BTs are attractive not only because they improve modularity, readability, and reactivity compared with conventional FSM formulations, but also because their explicit, compositional structure makes them a natural target for automated synthesis and repair with LLMs. In that sense, the same properties that make BTs easier for humans to inspect and modify also make them suitable for machine-assisted extension [Comparison between Behavior Trees and Finite State Machines] [Automatic Behavior Tree Expansion with LLMs for Robotic Manipulation].

The comparison can be sharpened further by considering structural editability and graphical complexity. Notes derived from [Comparison between Behavior Trees and Finite State Machines] highlight that inserting or removing a BT node can be treated as a local tree operation, whereas editing an FSM may require checking consistency across multiple transitions, and editing an HFSM remains local only within the relevant level of the hierarchy. The same source also frames readability in terms of the number of graphical elements required to represent a policy, arguing that the representation cost grows differently across BTs, FSMs, and HFSMs as the number of robot skills increases [Comparison between Behavior Trees and Finite State Machines]. These observations matter for human-robot interaction systems because maintainability is not only about whether a policy runs, but also about whether it can be inspected, revised, and validated efficiently as the behaviour set expands.

HFSMs occupy an important middle ground in this design space. They retain the event-driven semantics of FSMs while partially recovering modularity through hierarchical decomposition. A complex task can be factored into nested sub-machines that group related subtasks, which reduces some of the transition explosion found in flat FSMs. However, the hierarchy is still hand-crafted, and the switching semantics remain tied to state transitions rather than to the explicit control-flow nodes used in BTs [Comparison between Behavior Trees and Finite State Machines]. For that reason, HFSMs improve manageability but do not eliminate the broader trade-off between explicit reactive structure and transition-heavy coordination.

The attached design examples of the same mobile-robot task expressed as an FSM, a BT, and an HFSM reinforce these distinctions at the representation level. In the FSM view, the task unfolds as a sequence of named states connected by explicit completion events, with additional bookkeeping required for remembered information such as spoken instructions. In the BT view, the same task is represented compositionally through sequence, action, and condition nodes, with shared data placed on a blackboard. In the HFSM view, the task is decomposed into nested sub-machines that package intermediate phases more cleanly but still rely on event-driven transitions between phases. As a comparative lens, this example illustrates why BTs are often perceived as structurally closer to reusable behaviour composition, while FSMs and HFSMs remain closer to explicit control-flow engineering.

Practical adoption in robotics also supports the importance of BTs as an execution formalism. The Nav2 stack in ROS2 uses Behaviour Trees as the control substrate for navigation, exposing action, condition, decorator, and control nodes that can be assembled into reactive navigation policies. Examples such as goal-update checks, battery conditions, recovery nodes, and rate controllers show that BTs are not only theoretical abstractions, but also established engineering tools for coordinating long-running robotic actions under changing runtime conditions. This practical uptake strengthens the relevance of BT-oriented research, including LLM-assisted BT generation and repair, because it connects high-level policy synthesis to execution models that are already deployed in mature robotic software ecosystems.
